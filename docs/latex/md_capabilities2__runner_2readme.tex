 This package provides the {\ttfamily runner} API for abstract provision of capabilities. Runner plugins extend the execution functionality of the {\ttfamily capabilities} system. The ROS1 implementation used launch files to start capabilities. The ROS2 implementation uses runners. This allows for more flexibility in how capabilities are started and stopped, or how they are managed, and operate.\hypertarget{md_capabilities2__runner_2readme_autotoc_md25}{}\doxysection{\texorpdfstring{Runner archetypes}{Runner archetypes}}\label{md_capabilities2__runner_2readme_autotoc_md25}

\hypertarget{md_capabilities2__runner_2readme_autotoc_md31}{}\doxysubsection{\texorpdfstring{Launch\+Runner}{LaunchRunner}}\label{md_capabilities2__runner_2readme_autotoc_md31}
The {\ttfamily Launch\+Runner} inherits from {\ttfamily \doxylink{classcapabilities2__runner_1_1NoTriggerRunner}{capabilities2\+\_\+runner\+::\+No\+Trigger\+Runner}}, but it is intentionally deferred in the current codebase. The class and plugin entry are kept so that launch support can be restored once the replacement approach for the current ROS2 launch system is ready. For now, do not configure providers to depend on launch-\/file execution through this runner.\hypertarget{md_capabilities2__runner_2readme_autotoc_md32}{}\doxysubsection{\texorpdfstring{Creating a Custom runner}{Creating a Custom runner}}\label{md_capabilities2__runner_2readme_autotoc_md32}
The main idea is to allow users to create custom runners for their specific capabilities. Runners can be created to perform capabilities. The runner can be specified in a capability provider as the {\ttfamily runner} tag\+:

The runner {\ttfamily capabilities2\+\_\+runner\+::\+My\+Runner} should inherit from the {\ttfamily \doxylink{classcapabilities2__runner_1_1RunnerBase}{capabilities2\+\_\+runner\+::\+Runner\+Base}} or another like the {\ttfamily \doxylink{classcapabilities2__runner_1_1ActionRunner}{capabilities2\+\_\+runner\+::\+Action\+Runner}} class. The runner must implement the {\ttfamily start}, {\ttfamily stop}, and {\ttfamily trigger} methods, and then be registered as a plugin, using the {\ttfamily PLUGINLIB\+\_\+\+EXPORT\+\_\+\+CLASS} macro. See \doxysectlink{md_capabilities2__runner_2docs_2create__runners}{Creating Runners}{0} for more information.\hypertarget{md_capabilities2__runner_2readme_autotoc_md33}{}\doxysection{\texorpdfstring{Runner Execution Patterns}{Runner Execution Patterns}}\label{md_capabilities2__runner_2readme_autotoc_md33}
\hypertarget{md_capabilities2__runner_2readme_autotoc_md34}{}\doxysubsection{\texorpdfstring{Start -\/$>$ Stop}{Start -> Stop}}\label{md_capabilities2__runner_2readme_autotoc_md34}
The simplest runner execution pattern is to start the runner and then stop it. An example of this is the {\ttfamily Launch\+Runner}. This pattern represents a {\itshape {\bfseries{self-\/contained}}} capability. An example might be the action of a robot following another entity. This skill could be self-\/contained and runs continuously until stopped. This case assumes that the skill is continuously running and does not require any external triggers. ROS {\bfseries{Topic}} subscriptions and {\bfseries{Launch}} files are like this type.\hypertarget{md_capabilities2__runner_2readme_autotoc_md35}{}\doxysubsection{\texorpdfstring{Start -\/$>$ Trigger -\/$>$ Stop}{Start -> Trigger -> Stop}}\label{md_capabilities2__runner_2readme_autotoc_md35}
A more complex runner execution pattern is to start the runner, trigger it, and then stop it. This pattern represents a {\itshape {\bfseries{one-\/shot}}} capability. An example might be the action of a robot moving to a waypoint. This skill is triggered once and then stops.\hypertarget{md_capabilities2__runner_2readme_autotoc_md36}{}\doxysubsection{\texorpdfstring{Start -\/$>$ Trigger -\/$>$ Trigger -\/$>$ ... -\/$>$ Stop}{Start -> Trigger -> Trigger -> ... -> Stop}}\label{md_capabilities2__runner_2readme_autotoc_md36}
An even more complex runner execution pattern is to start the runner, trigger it multiple times, and then stop it. This pattern represents a {\itshape {\bfseries{repeating}}} capability. An example might be the action of a robot completing a state-\/machine or tree. This skill is triggered multiple times and then stops. This pattern (and the previous one) often implies that data is passed to and from the runner.\hypertarget{md_capabilities2__runner_2readme_autotoc_md37}{}\doxysubsection{\texorpdfstring{Start -\/$>$ End (no Stop)}{Start -> End (no Stop)}}\label{md_capabilities2__runner_2readme_autotoc_md37}
The final runner execution pattern is to start the runner and then end it without stopping. This pattern represents a challenge for the runner API, as it is not clear when the runner should be stopped. ROS communications patterns including {\bfseries{Services}} and {\bfseries{Actions}} are like this type.\hypertarget{md_capabilities2__runner_2readme_autotoc_md38}{}\doxysection{\texorpdfstring{Trigger Parameter Format}{Trigger Parameter Format}}\label{md_capabilities2__runner_2readme_autotoc_md38}
Runners can use parameters. These parameters are passed to the runner in the {\ttfamily trigger} function. For more information, see \doxysectlink{md_capabilities2__runner_2docs_2parameter__format}{Parameter Format}{0}.
